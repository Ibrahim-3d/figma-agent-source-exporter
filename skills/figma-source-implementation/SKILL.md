# Figma source implementation

## Purpose

Use this skill for **portable Figma → Agent source packs generated by Agent Source Exporter**. The pack is implementation evidence for 1:1 frontend work, not a literal application architecture.

Do not require live Figma REST or MCP access when the exported pack already contains the needed evidence. Do not ask the user to repeat information that can be recovered from the pack or the target repository.

## Evidence model

Treat the export as several complementary sources of truth:

- `manifest.json` defines export scope, page/frame mappings, enabled extraction options, counts, and extraction errors.
- `frames/**` is the **visual target** for final appearance and viewport-specific reconciliation. Never ship a reference frame screenshot as the implemented UI.
- `assets/images/**` and `assets/svg/**` are the preferred source for supplied static visual assets.
- `tokens/variables.json` and `tokens/styles.json` contain exact design-system evidence when exported.
- `components/index.json` describes component sets, variants, instances, property definitions, and referenced components.
- `document/pages/*.json` contains structured node evidence: geometry, Auto Layout, constraints, text, fills, effects, component references, and hierarchy.
- `typography/fonts.json` inventories font family/style usage. It does not include font binaries.
- Agent inference is allowed only after checking the available exported evidence and the target codebase.

There is no single universal priority when sources appear to conflict:

- for **visual appearance**, reconcile to the corresponding frame render;
- for **exact values and relationships**, prefer structured source data;
- for **asset identity**, prefer the exported original asset;
- for **missing or contradictory evidence**, inspect `manifest.json.errors`, record the uncertainty, and avoid inventing unsupported details.

## 0. Establish the implementation frame

Before modifying code, identify:

- target route, screen, component, or flow;
- target Figma page/frame and node ID where available;
- source frame dimensions and reference-render path;
- target repository stack and existing conventions;
- existing design-system components, tokens, and assets that may already match;
- required responsive states;
- relevant extraction warnings or missing evidence.

If the user names a target screen loosely, resolve it from the manifest and frame names before asking for clarification.

## 1. Read the pack before editing

Always inspect, in this order:

1. `manifest.json`;
2. `agent/README.md` when present;
3. the target entry under `frameReferences`;
4. the matching structured page JSON;
5. `assets/asset-map.json`;
6. relevant tokens, component data, font inventory, and exported assets.

Review every manifest error that touches the target frame, its assets, typography, components, or page.

If the export scope does not actually contain the requested target, stop treating the pack as complete evidence. State exactly what is missing.

## 2. Create a source map

Before implementation, create a compact mapping between the requested screen and the evidence used to build it. Use `agent/source-map.template.yaml` when available.

At minimum record:

```yaml
target:
  page: Marketing
  frame: Home / Desktop
  nodeId: "123:456"
  dimensions:
    width: 1440
    height: 5200

references:
  visual: frames/marketing/home__123_456@1x.png
  structure: document/pages/marketing__0_1.json

assets:
  hero: assets/images/<hash>.webp
  logo: assets/svg/marketing/logo__12_44.svg

implementation:
  route: /
  component: src/app/page.tsx
```

The source map is traceability, not busywork. Keep it small and update it if the implementation target changes.

## 3. Inspect the target codebase

Before creating new UI primitives:

- inspect the relevant route/component tree;
- inspect installed UI/design-system dependencies;
- search for matching components, assets, tokens, typography, utilities, layout primitives, and responsive patterns;
- reuse project-native components when they can express the design accurately;
- preserve application architecture, accessibility patterns, routing, data flow, and state conventions.

Do not replace a maintainable application structure with a Figma-shaped component tree.

## 4. Implement from evidence

### Assets

Use every required visible static asset in the position and role shown by the design.

Do not:

- redraw supplied SVGs;
- replace supplied images with placeholders;
- substitute "similar" icons;
- recreate logos in CSS;
- use the reference PNG as a background to fake the implementation.

When the codebase already contains an **exact** equivalent asset, reuse it instead of duplicating the exported file.

### Layout and geometry

Use structured geometry, Auto Layout, constraints, and multiple exported viewport frames to infer responsive behavior.

Translate Figma layout intent into semantic application layout. Absolute positioning is acceptable when the design genuinely requires it, not simply because Figma exposes coordinates.

### Typography

Use exported font usage, text properties, styles, and variables. If the required font files are not available in the export or project, do not silently substitute and claim fidelity; record the substitution or missing dependency.

### Tokens and styles

Prefer the target project's existing token system when values match. Map Figma variables/styles into that system rather than scattering hardcoded duplicates.

When no project token exists, introduce the smallest maintainable representation needed for the target.

### Components and variants

Use component metadata to understand repetition, variants, states, and relationships. Do not generate one application component for every Figma FRAME, GROUP, or INSTANCE.

### Interaction

The export primarily describes visual/source state. Implement interactions that are evident from component states, naming, supplied application requirements, or existing product behavior. Do not invent product behavior from a static frame alone.

## 5. Visual verification loop

When a reference frame exists:

1. run the target application;
2. render or screenshot the implementation at the **exact source viewport dimensions**;
3. compare against the corresponding file under `frames/**`;
4. diagnose causes rather than patching symptoms;
5. repeat until the requested screen reaches the intended 1:1 visual target or all remaining deltas are explicitly explained by missing/unsupported evidence.

Fix mismatches in this order:

1. page structure and major geometry;
2. container sizing and alignment;
3. typography metrics and text wrapping;
4. spacing and rhythm;
5. asset identity, crop, scale, and placement;
6. colors, borders, shadows, blur, gradients, and effects;
7. responsive behavior;
8. interactive and state-specific differences.

Do not alter unrelated pre-existing UI to make the comparison look better.

If no reference render was exported, state that pixel-level visual reconciliation is unavailable and verify against structured evidence only.

## 6. Completion gate

Do not call the implementation complete until all applicable checks pass:

- target page/frame is explicitly mapped;
- relevant manifest extraction errors were reviewed;
- visible static assets use exact exported or exact existing equivalents;
- no temporary Figma URLs or placeholders remain;
- typography and tokens are resolved or missing dependencies are documented;
- implementation follows the target codebase's architecture rather than the raw Figma layer tree;
- responsive behavior is supported by evidence or clearly identified assumptions;
- exact-dimension visual comparison was completed when a reference frame exists;
- remaining visual deltas or evidence gaps are reported explicitly.

A visible substituted, missing, or misproportioned supplied asset is a failure.

## Anti-patterns

Never:

- treat a screenshot as the only evidence when structured source exists;
- treat the screenshot itself as a production UI asset;
- approximate a value that is already available in the source pack;
- ignore `manifest.json.errors`;
- infer theme or viewport hints as authoritative design semantics;
- "improve" or redesign the source unless the user asks;
- create unnecessary wrappers/components to mirror Figma grouping;
- silently discard unsupported or missing states;
- claim pixel fidelity without rendering the implementation at the target dimensions.
